# ArcMassItems

Mass-native item storage, slots, equipment, quick bars, and visual attachments. Successor of the retired actor-side `UArcItemsStoreComponent` — all item state lives on Mass entities.

## Read these first

- `Source/ArcMassItemsRuntime/Operations/ArcMassItemOperations.h` — the mutation API surface.
- `Source/ArcMassItemsRuntime/Operations/ArcMassItemTransaction.h` — event batching contract.
- `Source/ArcMassItemsRuntime/Items/ArcItemData.h` — runtime item state + invariants.
- `Source/ArcMassItemsRuntime/Events/ArcMassItemEventSubsystem.h` — the delegate rail.
- `Source/ArcMassItemsRuntime/Attachments/ArcMassItemAttachmentSubsystem.h` — visual attachment driver.

## Architecture chain

`FArcItemDefinitionData` (`Items/ArcItemDefinitionData.h`, JSON record `.arcitem`, id `ArcItem:<guid>`; `TSet<FArcInstancedStruct>` fragment sets, keyed by **exact** struct name — definition-level `FindFragment` is exact-type, spec-level uses `IsChildOf`) → `FArcItemSpec` (creation recipe) → `FArcItemData` (mutable runtime state) stored in an `FInstancedStruct` inside `FArcMassReplicatedItem` inside the sparse `FArcMassItemStoreFragment`. `UArcMassItemStoreTrait` seeds one store per listed type plus a singleton `FArcMassItemEventFragment`. Multiple stores per entity = derive `FArcMassItemStoreFragment`.

**Heap-stability invariant:** `FArcItemData` heap blocks survive store-array mutation and `MoveItem` (the `FInstancedStruct` moves its heap pointer) — `FArcItemData*` caches are safe. Do NOT copy `FArcItemData` out of the store: the non-UPROPERTY caches (`InstancedData` views, `ScalableFloatFragments`, hierarchy pointers) don't survive copies.

**Item definitions are records.** References to an item definition are ids (`FArcNamedPrimaryAssetId`, `AllowedTypes = "ArcItem"`); `FArcItemDefinitionData::Find(Id)` resolves one (game thread, `FindJsonRecord`, a missing id warns once). `FArcItemSpec` holds only `ItemDefinitionId` and resolves on each `GetItemDefinition()` call. Only `FArcItemData` caches the record (`ItemDefinition`, not replicated). The server resolves it in `NewFromSpec` and builds the derived caches in `InitializeMass`; `RefreshItemDefinition()` re-resolves it and rebuilds `ScalableFloatFragments`, `ScalableFloatContext.ItemDefinition` and `ItemAggregatedTags`, and runs in `FArcMassReplicatedItem::PostReplicatedAdd/Change` on clients and from `UArcMassItemRecordSyncSubsystem` on `OnJsonRecordChanged` (items with that id and items holding one in `ItemsInSockets`). Code off the game thread reads only the item cache. Item equality and validity use the id (valid = id valid and cache resolved). Blueprint: `UArcItemsBPF::GetItemDefinition` returns the id; `BP_FindItemFragment`, `FindByItemTags`, `FilterByItemTags`, `FilterByTags` live on `UArcItemsBPF`. The module registers `FArcInstancedStruct` as a record wrapper; `FArcInstancedStruct::UpdateStructName()` is the one rule for `StructName`. See [ArcJsonAssets CLAUDE.md](../ArcJsonAssets/CLAUDE.md).

## Mutation contract

- **User-facing add/remove/destroy/move/equip go through `Commands/`** (`FArcMass*Command`, self-contained replicated commands). Direct `ArcMassItems::` ops calls are for server-internal systems (loot grants, station transfers, traits) and tests only.
- Ops are transactional (`FArcMassItemTransaction`, RAII): nesting on the same (Entity, StoreType) is safe — inner emits forward to the outer. Game-thread only; unsafe inside Mass processors unless the event fragment pre-exists (transaction commit may add the sparse fragment).
- `RemoveItem` full removal delegates to `DestroyItem`: every removal path fires `OnPreRemove`, detaches from the owner, clears the slot (SlotCleared event), and tears down attachments recursively.
- `AttachItem` validates: self-attach, already-owned, occupied attach slot, and ownership cycles are rejected (`return false`, no events).

## Item hierarchy caches — maintained ONLY by AttachItem/DetachItem

`OwnerItemCachedPtr`, `ItemsInSockets`, and the merged `ScalableFloatFragments` map (rebuilt via `FArcItemData::RebuildScalableFloatFragments()`: own definition wins per type, then first socket) are written exclusively by `AttachItem`/`DetachItem` (and `InitializeMass` for the definition-only base; `RefreshItemDefinition` rebuilds `ScalableFloatFragments` after the record changes or replicates). Never set them elsewhere. `FArcItemInstance::OwningItem` points at the owning `FArcItemData` (set in `SetItemInstances`). `OnItemAttachedTo`/`OnItemDetachedFrom` fragment callbacks fire from Attach/Detach.

## Two event rails — pick the right one

1. **Delegate rail (`UArcMassItemEventSubsystem`)** — the default for new game-thread listeners. MPSC queues drained post-actor-tick onto delegates. Global multicasts carry `(Entity, ItemId, …, const UScriptStruct* StoreType)` — filter by store in the handler. Per-entity API (`Add*ForEntity`) keys on (Entity, StoreType); unbind via `RemoveForEntity`; entity teardown evicts via `UArcMassItemAttachmentTagRemoveObserver → EvictEntity`. The generic `OnItemSlotChanged` fires for assign, clear, AND move — one subscription covers all slot transitions (see `UArcMassItemAttachmentSubsystem`, `UArcMassQuickBarAutoSelectSubsystem`, `UArcMassEquipmentSyncSubsystem` for the canonical adapter pattern: Initialize binds, Deinitialize removes, `EnsureCached()` EntityManager).
2. **Signal + event-fragment rail** — for Mass processors only (`UMassSignalProcessorBase` + `FArcMassItemEventFragment::Events`). Events live one frame: the next transaction commit prunes prior-frame entries, so consumers one frame later can miss OR re-see events. If you iterate `Events` and call anything that can run item ops, **copy the array first** — transaction commits mutate it mid-iteration. The retired `UArcMassQuickBarAutoSelectProcessor` died of exactly this.

## Item fragment lookup — use `ArcItemsHelper`

Use `ArcItemsHelper::FindFragment<T>(&Item)` (full traversal: definition → spec → owner → sockets) for authored fragments — UI/Icon/most fragments live on the item record. **Not `FArcItemData::FindSpecFragment<T>()`** — that's Spec-only (dynamic/runtime fragments) and silently returns null for definition-authored ones.

Companion accessors: `GetFragment<T>` = definition-only; `FindInstance`/`FindMutableInstance<T>` = per-entity instanced data; `ForEachFragment<T>` = iterate. Header: `ArcMassItemsRuntime/Items/ArcItemsHelpers.h`.

## Attachment handler lifecycle (`FArcMassAttachmentHandler`)

Driven by `UArcMassItemAttachmentSubsystem` from the delegate rail. Phases: `HandleItemAddedToSlot` (record the `FArcMassItemAttachment` in `State.ActiveAttachments` + claim socket) → `HandleItemAttach` (spawn UObjects into `State.ObjectsAttachedFromItem`, idempotent via `Contains`) → `HandleItemDetach` (destroy + clear map entry) → `HandleItemAttachmentChanged` (visual swap: the object-spawning handlers call `ReattachVisualObjects` — destroy old objects, respawn from the updated `VisualItemDefinition`; AnimLayer/CustomizableObject stay no-op). `ReconcileEntity`'s stale sweep resolves items across **all** `InterestedStoreTypes` before evicting. Entity teardown: `UArcMassItemAttachmentTagRemoveObserver` → `TeardownEntity` destroys all spawned objects.

## Equipment

`FArcMassEquipmentFragment::EquippedItems` (equipment slot tag → item id). Invariant: **equipped ⇒ slotted**. Maintained synchronously by `FArcMassEquipFromStoreCommand`/`FArcMassEquipFromDefinitionCommand`/`FArcMassUnequipCommand` (equip-over-occupied unequips the previous item first) and asynchronously by `UArcMassEquipmentSyncSubsystem` (OnItemRemoved/OnItemSlotCleared evict stale entries — covers cascades and direct unslot paths).

## Item activation

A slotted item is active or inactive (`FArcItemData::bIsActive`, replicated, not SaveGame). Activation fires the slot hooks (`OnItemAddedToSlot` on every `FArcItemFragment_ItemInstanceBase`, granted abilities and effects included) and adds the definition's `FArcItemFragment_Tags::GrantedTags` to the owner through `ArcAbilities::AddOwnedTags`; deactivation fires `OnItemRemovedFromSlot` and removes them. Attached (socketed) items follow their owner item.
- `ArcMassItems::ActivateItem` / `DeactivateItem` are idempotent through `bIsActive`.
- `AddItemToSlot` and `ChangeItemSlot` activate the item unless activation is deferred for the target slot. Slot removal, change, move and destroy deactivate an active item.
- **Deferral**: a Quick Bar bar with `FArcMassQuickBarEntry::bDeferItemActivation` (top level or in a group) defers activation for the item slots its quick slots bind (`QuickBar::IsItemActivationDeferred`). Such an item activates in `ActivateSlot` (before input binding) and deactivates in `DeactivateSlot`. Unbound slots (armor) activate on placement.

## QuickBar

`UArcMassQuickBarTrait::Configs` (several `UArcMassQuickBarConfig`, copied into `FArcMassQuickBarSharedFragment::Configs`) + one state fragment (`FArcMassQuickBarStateFragment`). Ops in `QuickBar/ArcMassQuickBarOperations.h`. Auto-select = `ArcMassItems::QuickBar::AutoSelect` free functions (testable directly), adapter `UArcMassQuickBarAutoSelectSubsystem` on the generic slot rail.
- **One store per config.** Each config declares exactly one `StoreType`; its bars only see items of that store. `BarId`/`GroupId` are unique across all configs of a trait (`ValidateTemplate`), so ops and commands take no store: `QuickBar::FindBar(EM, Entity, BarId)` resolves config, bar and group, and the store comes from `Config->StoreType`. Auto-select and `IsItemActivationDeferred` only consider configs whose store matches the event/item store.
- **Two axes: bar active, slot active.** Bar active is per bar (`FArcMassQuickBarStateFragment::BarStates`), seeded from `FArcMassQuickBarEntry::bActiveOnStart` by the trait (`QuickBar::SeedBarStates`; no `QuickBarSelectedActions` fire for seeded bars) and changed by `ActivateBar` / `DeactivateBar` / `CycleActiveBar`; read it with `QuickBar::IsBarActive`. A slot can be active only while its bar is active (`ActivateSlot` rejects slots of inactive bars); `QuickSlotsMode` decides which: `AutoActivateOnly` every filled slot, `Cyclable` exactly one (`ActivateSlot` deactivates the other; `DeactivateBar` remembers it in `LastActiveSlotId`, `ActivateBar` restores it or picks the first filled slot passing the `CycleSlot` checks), `ManualActivationOnly` only explicitly activated slots (not remembered). `AddAndActivateSlot` activates the new slot per mode only on an active bar (`Cyclable`: only with `bAutoSelect` and no other active slot). "Bar active as a whole" = `AutoActivateOnly` + `bActiveOnStart`.
- **Groups (`FArcMassQuickBarGroup`).** At most one bar of a group is active: `ActivateBar` deactivates the group's other active bar first; `GetActiveBarInGroup` derives it from the per-bar state. `CycleActiveBar` (group `bCyclable`) activates the next bar in `Bars` order that holds at least one item. Bars that may be active together are not grouped. `ValidateTemplate`: at most one `bActiveOnStart` bar per group, and every grouped bar sets `bDeferItemActivation` and an `ItemSlotId` on every slot, so the items of an inactive grouped bar are inactive.
- **Child bars (`ParentBarId`).** A quick slot is always addressed by the pair (BarId, QuickSlotId). A bar with a valid `ParentBarId` is the single child bar of that parent bar; the parent must be a bar in the trait's configs, not itself, not a child bar (no nesting), have no other child bar, and not be `AutoActivateOnly`: a parent bar, like every `Cyclable` bar, has at most one active slot (`ActivateSlot` deactivates the other first). When an item with `FArcItemFragment_QuickBarItems` is added to a parent slot, its `ItemsToAdd` (up to the child bar's slot count) are created unslotted in the child bar's config store and recorded on that slot's state entry (`FArcMassQuickBarActiveSlot::ChildItemIds`). Activating the parent slot binds its children in order into the child bar's quick slots and item slots and activates them; deactivating it unbinds them (quick slots cleared, items unslotted, kept in the store); removing the parent item from the slot destroys them. Child bars are outside the bar-active axis and driven only by their parent (auto-select ignores them on every path; every QuickBar command taking a bar rejects them) and must defer item activation, set `ItemSlotId` on every slot, stay out of groups, not be `Cyclable` and not set `bActiveOnStart` — all checked in `ValidateTemplate`.
- `QuickBar::GetActiveItem(EM, Entity, RequiredItemTags)` returns the first active item in an active quick slot of any bar whose aggregated item tags contain `RequiredItemTags` (e.g. `Item.Weapon` for the active weapon), read from the store of the config owning that bar.
- User-facing slot activation goes through the replicated commands `FArcMassActivateQuickSlotCommand`, `FArcMassDeactivateQuickSlotCommand` and `FArcMassCycleQuickSlotCommand`; bar switching through `FArcMassActivateQuickBarCommand` (bar) and `FArcMassCycleQuickBarCommand` (cyclable group, `Direction` != 0). There is no deactivate-bar command.
- **Prediction (QuickBar is client-authoritative).** These five selection commands opt in to replicated-command prediction (`ExecutesOnClient`): on a client without authority they run locally first, return false before changing state when they cannot run (then nothing is sent), capture the selection of the bars they touch (`QuickBar::CaptureBarSelection` / `CaptureGroupSelection`) and restore it in `UndoPrediction` (`QuickBar::RestoreSelection`). The cycle commands send the client's pick (`ResolvedQuickSlot` / `ResolvedQuickBar`) and the server activates it instead of cycling. Add/remove quick slot commands do not predict (they mutate item stores). Standalone/server: no prediction.

## Tests

`ArcGame/Plugins/ArcX/Tests/ArcMassItemsTest` (CQTest). Helpers: `ArcMassItems::TestHelpers` (`CreateAttachmentEntity`, `CreateDualStoreAttachmentEntity`, `DrainAttachmentEvents` = manual queue drain, `WriteWithMarkerFragment`/`WriteWithLifecycleRecorder`/`WriteWithScalableFragment` = variant record with the fragment, returns its id, `LifecycleLog()`, `SendMassItemCommand`), `QuickBar::TestHelpers` (`BuildQuickBarConfig`, `CreateQuickBarEntity` = seeds bar state like the trait, `RunAutoSelect` = event-copy driver for the free functions). Non-PIE classes use `FActorTestSpawner` — `UWorldSubsystem`s (event, attachment, equipment-sync, Mass) DO exist in its world and can be driven by manually draining (`DrainAttachmentEvents`); what needs PIE is the *automatic* post-actor-tick drain and full game-mode plumbing — those tests are PIE-gated (`ENABLE_ARC_STANDALONE_PIE_TEST`). Item fixtures resolve via `DefaultArcTests.ini` ids of the `.arcitem` records under `ArcCoreTest/Content` — if a fixture test fails on a missing fragment/tag, suspect the record↔ini id before the code. Tests that need their own definition write records with `FArcItemTestRecordFiles` (`ArcCoreTest/Source/ArcSharedTestHarness/ArcItemTestRecordFiles.h`: write, index, removed at teardown).
